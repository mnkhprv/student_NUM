Сэдэв: Deadlock-ыг C хэл дээр симуляц хийх, шинжлэх, сайжруулах

Орчин: Ubuntu, kernel 7.0.0-38-generic, gcc (Ubuntu 15.2.0-16ubuntu1) 15.2.0, POSIX Threads

Нэр: ____________  Код: 23B1NUM0114  Бүлэг: ______

Compile хийх, ажиллуулах, цэвэрлэх:

```bash
make
./deadlock     # гацна, Ctrl+C дарж зогсооно
```

Файлууд: `deadlock.c` (жишээ код), `safe.c` (lock ordering), `trylock.c` (нэмэлт даалгавар).

## 1. Зорилго

Deadlock-ийг pthread бүхий програм дээр ажиглах, яагаад үүсч байгааг тайлбарлах,
lock авах дарааллыг өөрчилж deadlock-гүй хувилбар хийх.

## 2. Онолын үндэслэл

Deadlock гэдэг нь хоёр ба түүнээс дээш thread бие биенийхээ барьж буй нөөцийг хүлээж,
хэн нь ч цааш ажиллаж чадахгүй болсон төлөв. Deadlock үүсэхэд 4 нөхцөл зэрэг биелэх ёстой:
Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait. Аль нэгийг нь эвдвэл
deadlock үүсэхгүй.

- **Lock / mutex** - нэг цагт зөвхөн нэг thread эзэмшиж болох "түгжээ".
  `pthread_mutex_lock` авна, `pthread_mutex_unlock` суллана.
- **Critical section** - lock ба unlock хоёрын хоорондох, shared нөөцөд хандах кодын хэсэг.

## 3. Жишээ кодын тайлбар (Даалгавар 1)

| Хэсэг | Үүрэг |
|---|---|
| `pthread_mutex_t lock1, lock2` | Глобал хувьсагч. Хоёр thread хоёулаа харах ёстой тул глобал. Хоёр нөөцийг төлөөлнө. |
| `pthread_mutex_init / destroy` | main дотор mutex-ийг эхлүүлж, төгсгөлд нь устгана. |
| `thread1_func` | lock1 -> (1 секунд унтана) -> lock2 гэсэн дарааллаар авна, дараа нь эсрэг дарааллаар суллана. |
| `thread2_func` | lock2 -> (1 секунд унтана) -> lock1 гэсэн **эсрэг** дарааллаар авна. |
| `sleep(1)` | Thread бүр эхний lock-оо аваад хүлээх хугацаа. Энэ хугацаанд нөгөө thread өөрийн эхний lock-ийг амжиж авна. |
| `main()` | 2 thread үүсгэж (`pthread_create`), хоёулаа дуустал хүлээнэ (`pthread_join`), эцэст нь "Main: програм дууслаа" гэж хэвлэнэ. |

## 4. Туршилтын үр дүн (Даалгавар 2, 3)

`./deadlock`-ийг 3 удаа ажиллуулсан (5 секундын timeout-тай). 3 удаа бүгд гацсан.

Ажиллуулалт 2-ын гаралт:

```
Thread 1: lock1 авах гэж байна...
Thread 1: lock1 авлаа
Thread 2: lock2 авах гэж байна...
Thread 2: lock2 авлаа
Thread 1: lock2 авах гэж байна...
Thread 2: lock1 авах гэж байна...
```

Ажиллуулалт 1-д Thread 2 түрүүлж эхэлсэн, гэхдээ эцсийн үр дүн адил - дээрх 6 мөрийн
дараа юу ч хэвлэгдээгүй, "lock2 авлаа", "ажил дууслаа", "Main: програм дууслаа" гарсангүй.

| № | Эхэлж хэвлэсэн | Сүүлийн мөр | Үр дүн |
|---|---|---|---|
| 1 | Thread 2 | Thread 1: lock2 авах гэж байна... | Гацсан |
| 2 | Thread 1 | Thread 2: lock1 авах гэж байна... | Гацсан |
| 3 | Thread 1 | Thread 2: lock1 авах гэж байна... | Гацсан |

**Хаана гацаж байна вэ?** Thread 1 `pthread_mutex_lock(&lock2)` дээр, Thread 2
`pthread_mutex_lock(&lock1)` дээр зогссон. Main нь `pthread_join(t1)` дээр хүлээсээр байна.

**Яагаад?** Thread 1 lock1-ийг барьж, lock2-ийг хүлээж байна. lock2-ийг Thread 2 барьж байгаа,
тэр нь lock1-ийг хүлээж байна. Хоёулаа нөгөөгөө суллахыг хүлээж байгаа ч хэн нь ч суллахгүй.

```
Thread 1 --барьж байна--> lock1 --хүлээж байна--> Thread 2
Thread 2 --барьж байна--> lock2 --хүлээж байна--> Thread 1
```

## 5. 4 нөхцөл энэ код дээр (Даалгавар 4)

| Нөхцөл | Код дээр |
|---|---|
| Mutual Exclusion | `pthread_mutex_t` нэг цагт нэг л thread-д байна. lock1-ийг Thread 1 барьж байхад Thread 2 авч чадахгүй. |
| Hold and Wait | Thread 1 lock1-ээ суллалгүй барьсаар `pthread_mutex_lock(&lock2)` дээр хүлээнэ. Thread 2 ч мөн адил. |
| No Preemption | Mutex-ийг зөвхөн эзэмшигч thread нь `unlock` хийж суллана. OS эсвэл нөгөө thread хүчээр авч чадахгүй. |
| Circular Wait | Thread 1 -> lock2 (Thread 2-т) -> Thread 2 -> lock1 (Thread 1-д) -> Thread 1. Тойрог үүссэн. |

## 6. Сайжруулсан кодын тайлбар (Даалгавар 5)

`safe.c` - хоёр thread нэг `safe_thread_func` функцийг ажиллуулна, нэрийг аргументаар
дамжуулна. Хоёулаа **lock1 -> lock2** дарааллаар авна.

Гаралт (2 удаа ажиллуулсан, 2 удаа ижил, ~2.0 секунд):

```
Thread 1: lock1 авах гэж байна...
Thread 1: lock1 авлаа
Thread 2: lock1 авах гэж байна...
Thread 1: lock2 авах гэж байна...
Thread 1: lock2 авлаа
Thread 1: critical section-д ажиллаж байна...
Thread 1: ажил дууслаа
Thread 2: lock1 авлаа
Thread 2: lock2 авах гэж байна...
Thread 2: lock2 авлаа
Thread 2: critical section-д ажиллаж байна...
Thread 2: ажил дууслаа
Main: deadlock үүсгэлгүй програм дууслаа
```

Thread 2 lock1 дээр хүлээж байх үедээ ямар ч lock бариагүй байна. Тиймээс Thread 1 lock2-ийг
саадгүй аваад, ажлаа дуусгаад хоёр lock-оо суллана. Дараа нь Thread 2 үргэлжилнэ.

## 7. Харьцуулсан шинжилгээ (Даалгавар 6)

| | `deadlock.c` | `safe.c` |
|---|---|---|
| Lock авах дараалал | T1: lock1->lock2, T2: lock2->lock1 | Хоёулаа lock1->lock2 |
| Үр дүн (3/2 удаа) | 3 удаа бүгд гацсан | 2 удаа бүгд дууссан |
| "Main: ... дууслаа" | Хэвлэгдээгүй | Хэвлэгдсэн |
| Circular wait | Байгаа | Байхгүй |
| Хугацаа | Хязгааргүй (Ctrl+C) | ~2 секунд |

Deadlock яагаад арилсан бэ? Бүх thread lock-уудыг нэг ижил дарааллаар авбал lock2-ийг
барьж байгаа thread заавал lock1-ийг аль хэдийн барьсан байна. Тэгэхээр "lock2-ийг барьчихаад
lock1-ийг хүлээх" тохиолдол гарахгүй, тойрог хүлээлт үүсэх боломжгүй. Бусад 3 нөхцөл
(mutual exclusion, hold and wait, no preemption) хэвээрээ ч circular wait алга болсон тул
deadlock үүсэхгүй. Сул тал нь: Thread 2 нь Thread 1 дуустал хүлээдэг тул зэрэг ажиллах нь
багасна.

## 8. Нэмэлт даалгавар: trylock (Даалгавар 7)

`trylock.c` - lock-ийн дарааллыг анхных шиг **эсрэг** хэвээр үлдээсэн. Харин хоёр дахь lock-ийг
`pthread_mutex_trylock`-оор авна. Энэ функц lock завгүй бол хүлээлгүй шууд `EBUSY` буцаана.
Тэгвэл thread эхний lock-оо суллаад, хэсэг хүлээгээд (Thread 1 - 0.2 сек, Thread 2 - 0.7 сек)
дахин оролдоно. Ингэснээр **Hold and Wait** нөхцөл эвдэрнэ.

3 удаа ажиллуулсан үр дүн:

| № | Thread 1 оролдлого | Thread 2 оролдлого | Дууссан эсэх |
|---|---|---|---|
| 1 | 4 | 4 | Тийм |
| 2 | 1 | 2 | Тийм |
| 3 | 2 | 1 | Тийм |

Ажиллуулалт 2-ын гаралт:

```
Thread 2: lock2 авлаа (оролдлого 1)
Thread 1: lock1 авлаа (оролдлого 1)
Thread 2: lock1 завгүй, lock2-ийг сулласан
Thread 1: lock2 авлаа
Thread 1: critical section-д ажиллаж байна...
Thread 1: ажил дууслаа (1 оролдлого)
Thread 2: lock2 авлаа (оролдлого 2)
Thread 2: lock1 авлаа
Thread 2: critical section-д ажиллаж байна...
Thread 2: ажил дууслаа (2 оролдлого)
Main: trylock ашиглаж deadlock-оос гарлаа
```

Ажиллуулалт 1-д хоёр thread хэд хэдэн удаа зэрэг lock-оо суллаж, дахин зэрэг авсан
(4 оролдлого). Энэ бол **livelock**-ийн шинж: thread-үүд гацаагүй, ажиллаж байгаа ч урагшлахгүй.
Хүлээх хугацааг өөр өөр (0.2 ба 0.7 сек) болгосноор тэд эцэст нь давхцахаа больж дууссан.
Хэрэв хоёулаа яг ижил хугацаа хүлээвэл удаан давтагдаж магадгүй.

## 9. Хэлэлцүүлгийн асуултууд

1. **Deadlock ба starvation-ийн ялгаа.** Deadlock-д бүлэг thread бие биенээ хүлээж, хэн нь ч
   хэзээ ч урагшлахгүй. Starvation-д систем ажиллаж байгаа, бусад thread нөөц авч байгаа ч
   нэг thread-д дараалал байнга ирэхгүй (жишээ нь priority бага). Deadlock-ийг гаднаас
   оролцохгүйгээр арилгах боломжгүй, starvation нөхцөл өөрчлөгдвөл өөрөө арилж болно.

2. **`sleep(1)`-ийг арилгавал deadlock үргэлж үүсэх үү?** Үгүй. `sleep(1)`-гүй хувилбарыг
   200 удаа ажиллуулахад (1 секундын timeout) **191 удаа дууссан, 9 удаа гацсан**. Нэг thread
   хоёр lock-оо маш хурдан аваад суллачихдаг тул нөгөө нь ихэнхдээ амжихгүй. Гэхдээ
   scheduler хоёр thread-ийг яг эхний lock-ийн дараа солих үед deadlock гарна. Тэгэхээр
   `sleep` нь deadlock-ийг үүсгэдэггүй, зөвхөн гарах магадлалыг бараг 100% болгодог.
   Алдаа код дотор байсаар байна.

3. **trylock deadlock-оос бүрэн сэргийлж чадах уу?** Зөв ашиглавал deadlock-оос сэргийлнэ,
   учир нь thread lock барьсаар хүлээхгүй (hold and wait эвдэрнэ). Гэхдээ бүх асуудлыг
   шийдэхгүй: (1) livelock үүсч болно - миний туршилтад 4 удаа давтагдсан; (2) нэг thread
   байнга ялагдаж starvation болж болно; (3) зөвхөн 2 дахь lock дээр биш, бүх газар trylock
   хийж, бүтэлгүйтвэл барьсан бүх lock-оо суллах ёстой. Нэг газар мартвал deadlock буцаж гарна.

4. **3 thread, 3 lock бүхий deadlock-ийг хэрхэн дүрслэх вэ?** Resource allocation graph-аар:
   T1 L1-ийг барьж L2-ийг хүлээнэ, T2 L2-ийг барьж L3-ийг хүлээнэ, T3 L3-ийг барьж L1-ийг хүлээнэ.

   ```
   T1 -> L2 -> T2 -> L3 -> T3 -> L1 -> T1
   ```

   Граф дээр тойрог байгаа бөгөөд lock бүр нэг instance-тай тул энэ нь deadlock.
   Шийдэл нь мөн адил: бүгд L1 -> L2 -> L3 дарааллаар авах.

5. **Бодит OS-д ямар нөөц дээр deadlock гардаг вэ?** Kernel доторх mutex/spinlock,
   өгөгдлийн сангийн мөр, хүснэгтийн lock (хоёр transaction эсрэг дарааллаар update хийх),
   файлын lock (`flock`), принтер зэрэг төхөөрөмж, pipe (хоёр процесс бие биенээсээ уншихыг
   хүлээх), санах ой (хоёр процесс нэмэлт санах ой хүлээх).

## 10. Дүгнэлт

Энэ лабораторид хоёр thread хоёр lock-ийг эсрэг дарааллаар авахад deadlock 3 удаа бүгд
үүссэнийг харлаа - програм 6 мөр хэвлээд зогссон, "Main: програм дууслаа" гарсангүй. Кодоос
deadlock-ийн 4 нөхцөл бүгд олдсон. Lock-ийг хоёр thread-д ижил дарааллаар (lock1 -> lock2)
авахуулахад circular wait арилж програм ~2 секундэд хэвийн дууссан. Нэмэлтээр trylock
ашиглахад эсрэг дараалалтай ч програм дууссан, гэхдээ livelock (4 удаа давтагдсан) гарч
болохыг ажигласан. `sleep(1)`-гүй үед deadlock 200-аас 9 удаа гарсан нь deadlock нь санамсаргүй,
давтан гаргахад хэцүү алдаа гэдгийг харуулж байна. Иймд lock ordering бол хамгийн энгийн
бөгөөд найдвартай арга юм.
