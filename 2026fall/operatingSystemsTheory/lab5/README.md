## III хэсэг - Дадлага 1: hello_threads

Thread-ийн тоог 3 болгож, ids = {1, 2, 3} өгсөн. 3 удаа ажиллуулсан үр дүн:

| Ажиллуулалт | Хэвлэх дараалал | Тайлбар |
|---|---|---|
| 1 | Thread 2, Thread 1, Thread 3 | Main-ийн эхний мөр, дараа нь thread-үүд, төгсгөлд Main |
| 2 | Thread 2, Thread 1, Thread 3 | Ижил |
| 3 | Thread 2, Thread 1, Thread 3 | Ижил |

Миний компьютер дээр 3 удаа ижил дараалал гарсан. Гэхдээ энэ нь баталгаа биш.

**Яагаад thread 1 заавал түрүүнд хэвлэгдэхгүй вэ?**
Thread-үүдийг OS-ийн scheduler хуваарилдаг. Thread 1 эхэлж үүссэн ч CPU цөм дээр
хэзээ гүйх нь scheduler-ээс хамаарна. Тиймээс хэвлэх дараалал хоорондоо өөр байж болно.
Join нь зөвхөн Main-ийн төгсгөлийн мөр бүх thread дууссаны дараа хэвлэгдэхийг
баталгаажуулна.

## IV хэсэг - Дадлага 2: Race condition

А. 2 thread × 500000 (`race_counter.c`, -O0):

| № | Thread | LOOPS | Хүлээгдсэн | Бодитоор гарсан |
|---|---|---|---|---|
| 1 | 2 | 500000 | 1000000 | 626836 |
| 2 | 2 | 500000 | 1000000 | 615554 |
| 3 | 2 | 500000 | 1000000 | 501035 |

Б. 3 thread × 100000 (`-DTHREADS=3 -DLOOPS=100000`):

| № | Thread | LOOPS | Хүлээгдсэн | Бодитоор гарсан |
|---|---|---|---|---|
| 1 | 3 | 100000 | 300000 | 127313 |
| 2 | 3 | 100000 | 300000 | 136481 |
| 3 | 3 | 100000 | 300000 | 151458 |

Үр дүн бүрт хүлээгдсэнээс бага, мөн ажиллуулах бүрт өөр гарсан.

**Яагаад ингэж гарав?** `counter++` нь нэг үйлдэл биш: (1) санах ойгоос уншина,
(2) 1 нэмнэ, (3) буцааж бичнэ. Хоёр thread нэг утгыг уншаад тус тусдаа 1 нэмээд бичвэл
нэг нэмэлт алга болно. Үүнийг race condition (data race) гэнэ.

ThreadSanitizer-ээр шалгахад (`gcc -g -O1 -fsanitize=thread -pthread`) `counter` дээр
"data race" гэсэн анхааруулга гарсан (race_counter.c:18, нэг thread уншиж, нөгөө нь бичсэн).

## V хэсэг - Дадлага 3: Mutex

| Туршилт | Expected | Observed | Дүгнэлт |
|---|---|---|---|
| Mutex run 1 | 1000000 | 1000000 | Зөв |
| Mutex run 2 | 1000000 | 1000000 | Зөв |
| Mutex run 3 | 1000000 | 1000000 | Зөв |

**Яагаад mutex дээр зөв дүн гарч байна вэ?**
`counter++` нь lock ба unlock-ийн дунд (critical section) байгаа тул нэг цагт зөвхөн
нэг thread уншиж-нэмж-бичнэ. Нэг thread дуустал нөгөө нь хүлээнэ, тиймээс нэмэлт алдагдахгүй.

**Mutex-ийг давталтын гадна байрлуулбал яах вэ?**
Дүн зөв хэвээр байна, гэхдээ нэг thread бүх давталтаа дуустал нөгөө нь хүлээнэ.
Тэгэхээр thread-үүд бараг зэрэг ажиллахаа больж, concurrency буурна. Critical section-ийг
аль болох богино байлгах нь дээр.

## VI хэсэг - Банкны програм (`bank.c`)

- Эхний balance = 1000. Deposit thread 50-г 10 удаа нэмнэ, withdraw thread 30-г 10 удаа хасна.
- Хоёр thread нэг `balance` хувьсагч ашиглана, mutex-ээр хамгаалсан.
- Withdraw нь lock авсны дараа `balance >= 30` эсэхийг шалгана. Хүрэлцэхгүй бол
  хасахгүй, `rejected`-г нэмнэ.
- Main нь хоёр thread-ийг join хийж, эцсийн balance болон rejected-ийг хэвлэнэ.
  pthread функц бүрийн алдааны кодыг шалгасан.

Хүлээгдэх balance: 1000 + 10×50 − 10×30 = 1200.

| Тест | Тохиргоо | Хүлээгдэж буй | Гарсан |
|---|---|---|---|
| A: Үндсэн | balance=1000, +50×10, −30×10 | balance=1200, rejected=0 | balance=1200, rejected=0 |
| B: Хүрэлцэхгүй | balance=20, зөвхөн withdraw 1 удаа (`./bank b`) | balance=20, rejected=1 | balance=20, rejected=1 |
| C: Давтан | A-г 3 удаа | 3 удаа 1200 | 1200, 1200, 1200 |

## VII хэсэг - Шалгах асуулт

1. **Process ба Thread-ийн 2 гол ялгаа.** Process өөрийн тусдаа виртуал санах ойтой,
   харин нэг process-ийн thread-үүд код, heap, global өгөгдлөө хуваалцана. Thread бүр
   өөрийн stack-тэй. Process хооронд өгөгдөл солилцоход IPC хэрэгтэй, thread-үүд
   shared memory-г шууд ашиглана.
2. **pthread_create()** нь одоо байгаа process дотор шинэ thread үүсгэж, өгсөн
   функцийг шинэ thread дээр ажиллуулна.
3. **pthread_join()** нь заасан thread дуустал хүлээнэ. Үгүй бол main эхлээд дуусаж,
   бусад thread дуусаагүй байхад програм таслагдаж болно. Мөн thread-ийн нөөцийг
   чөлөөлөхөд хэрэгтэй.
4. **Race condition / data race** нь хоёр ба түүнээс дээш thread нэг өгөгдөлд зэрэг хандаж,
   түүний дор хаяж нэг нь бичих, мөн үр дүн нь ажиллах дарааллаас хамаарч буруу болох нөхцөл.
5. **Mutex** нь shared өгөгдөлд нэг цагт зөвхөн нэг thread хандахыг баталгаажуулж,
   race condition-ийг (өгөгдлийн алдагдлыг) шийднэ.

**Дүгнэлт.** Энэ лабораторид thread нь нэг process-ийн санах ойг хуваалцдаг тул
хурдан хамтран ажиллах боломжтой ч, синхрончлолгүй бол `counter++` шиг энгийн үйлдэл
хүртэл буруу дүн өгдгийг харлаа (1000000-ийн оронд ойролцоогоор 500000-630000).
Mutex ашиглахад дүн 3 удаа бүгд зөв гарсан. Банкны програмд balance-ийг mutex-ээр
хамгаалж, шалгалтыг lock дотор хийснээр сөрөг үлдэгдэл үүсэхээс сэргийлсэн.
Гэхдээ mutex нь thread-үүдийг түр хүлээлгэдэг тул critical section-ийг богино байлгах хэрэгтэй.
